# Execution Timeout Policy

Этот документ задаёт обязательные таймауты для интерактивной работы над 2D-игрой и ассетами вместе с `ref2game`, `ASSET_PRODUCTION_PIPELINE.md` и `ASSET_TASK_TRACKER.md`.

Цель: ни один интерактивный ход не должен выглядеть как бесконечно зависший. Долгая операция обязана либо завершиться, либо оставить воспроизводимый checkpoint и вернуть управление пользователю.

## Hard deadline

- Максимальная длительность одного непрерывного interactive attempt: **20 минут wall-clock**.
- На отметке **15 минут** запрещено начинать новую дорогую генерацию, полный rebuild или новый длинный CI run. Разрешены только короткая проверка, сохранение checkpoint и подготовка результата.
- На отметке **18 минут** прекращаются все необязательные polish/critic/retry шаги.
- На отметке **20 минут** работа в текущем ходе останавливается независимо от причины. Нужно вернуть пользователю текущий статус, точный blocker/current step и checkpoint, с которого следующий ход может продолжить работу.

## No-progress watchdog

Если в течение **5 минут** нет наблюдаемого прогресса — нового файла, нового commit SHA, смены CI state, нового QA результата или иного проверяемого результата — текущий способ считается зависшим.

После 5 минут без прогресса нужно:

1. прекратить ожидание/повтор того же действия;
2. сохранить доступный checkpoint;
3. один раз перейти на альтернативный технический путь;
4. если альтернативный путь тоже не даёт прогресса — завершить ход с blocker report, не ждать 20 минут молча.

## Retry budget

- Одна и та же внешняя операция не повторяется бесконечно.
- **Две одинаковые ошибки подряд** для одного API/tool/method означают немедленную смену способа или остановку этого шага.
- Не делать серию почти одинаковых image-generation calls. Один call = один самостоятельный asset/part sheet согласно `ref2game`.
- Для одного asset в одном ходе допускается максимум **2 production-generation attempts**, если второй исправляет конкретный дефект первого. После этого — checkpoint + review, а не бесконечная регенерация.

## CI / GitHub Actions

- Не держать ход открытым частым polling одного и того же workflow.
- После запуска CI проверять только значимые смены состояния.
- Если CI не завершился к 15-минутной отметке хода, не запускать новый CI и не делать дополнительные дорогие изменения.
- Если CI всё ещё выполняется к hard deadline, вернуть run id / commit SHA / текущий job state и завершить ход. Следующий ход начинает с проверки этого же run, а не запускает новый без причины.

## Image generation and image processing

- Перед imagegen должен существовать отдельный asset prompt; нельзя передавать весь разговор как концепт-задачу.
- Один imagegen call генерирует только один production asset или один part sheet.
- Resize / alpha cleanup / quantize / conversion выполняются одним batch-проходом, а не цепочкой многочисленных почти одинаковых операций.
- После успешной генерации сначала сохранить original/checkpoint, затем выполнять destructive processing.

## Git writes

- Предпочитать один `tree -> commit -> ref` для набора связанных изменений вместо десятков последовательных file commits.
- Бинарные ассеты импортировать как Git blob/tree, а не многократно пробовать несовместимый text-file API.
- После двух одинаковых ошибок update/ref API сменить способ или ветку с безопасным base SHA; не повторять одинаковый вызов циклом.

## Checkpoint before timeout

Перед остановкой по timeout, когда это технически возможно, сохранить:

- текущий source/original;
- candidate/work intermediates;
- tracker state (`running`, `failed` или `blocked` с причиной);
- commit SHA / branch;
- CI run id, если он был запущен;
- точный следующий шаг.

Следующий интерактивный ход обязан сначала восстановить этот checkpoint согласно `ASSET_TASK_TRACKER.md`, а не начинать дорогие стадии заново.

## Progress messages

Не отправлять отдельное пользовательское сообщение после каждой внутренней операции. Прогресс группируется по крупным стадиям:

```text
asset/source
-> runtime/code
-> QA
-> build/delivery
```

Сообщение о ходе отправляется при завершении стадии, при смене стратегии или при blocker/timeout.

## Главное правило

**20 минут — абсолютный максимум одного непрерывного интерактивного attempt.** Если задача требует больше времени, она разбивается на resumable steps с checkpoint между ними; пользователь не должен вручную нажимать Stop из-за бесконечного ожидания.
