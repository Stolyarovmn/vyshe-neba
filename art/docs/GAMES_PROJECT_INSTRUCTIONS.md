# Инструкции для настроек ChatGPT Project «Games»

Это **готовый текст для поля Project instructions**. Он должен быть скопирован пользователем в настройки проекта; запись файла в GitHub **не изменяет** настройки ChatGPT автоматически. Project instructions помогают соблюдать процесс, но не заменяют реальные права доступа, проверки и CI.

---

Работай над игрой «Выше неба» (`Stolyarovmn/vyshe-neba`) строго по каноническому production pipeline. Не придумывай факты, углы камеры, размеры, статусы, SHA, наличие файлов или результаты тестов.

**Перед КАЖДЫМ запросом по игре**:
1. Прочитай актуальные `game-production:AGENTS.md`, `art/docs/ASSET_PRODUCTION_PIPELINE.md`, `art/docs/PRODUCTION_CONTRACT_V2.md`, `art/docs/RUNTIME_BRANCH_CONTRACT.md`, `art/docs/ASSET_GENERATION_RUNBOOK.md`, `art/docs/ASSET_TASK_TRACKER.md`, `art/docs/EXECUTION_TIMEOUT_POLICY.md`, `art/style_bible.txt`, `art/placeables/PRODUCTION_MANIFEST.md`, `art/placeables/PIPELINE_CONFIG.json` и skill `https://github.com/studioigor/ref2game/blob/main/codex/SKILL.md`. Для острова прочитай `art/placeables/BASE_ISLAND_LAYOUT.json`. Если файл недоступен, прямо укажи blocker, не симулируй чтение. Для branch/storage/promotion semantics `RUNTIME_BRANCH_CONTRACT.md` имеет приоритет над более старым текстом pipeline/tracker.
2. Проверь реальные GitHub branches/commit SHA и нужные файлы. `game-production` — production/history ветка: docs, tools, approved production art, provenance и QA. `main` — чистая runtime/build ветка и текущий default branch: актуальный runtime сверяй с `main:game/src/render/manifest.js` и доступными тестами на том же commit. Не предполагай `game-build`, `clean-src` как canonical build branch или legacy `outputs/rocket` без проверки.
3. Сначала восстанови checkpoint/asset tracker; затем определи тип ассета, ID, эпоху, gameplay role, состояние, референсы и обязательные контракты. Для нового/изменяемого ассета используй `art/docs/ASSET_BRIEF_TEMPLATE.md`; неизвестное помечай `UNKNOWN`, критически недостающее — `BLOCKED`. Если для ассета есть `art/briefs/*.preflight.json`, сначала проверь его `tools/art_pipeline/validate_generation_preflight.py`.
4. Для production imagegen: **один вызов — один asset или part sheet** и одна эпоха для anchor-generation. Фактический prompt собирай через `tools/art_pipeline/build_generation_request.py`, чтобы `art/style_bible.txt` был вставлен дословно, без ручного пересказа. Оригинал без обработки архивируй в Google Drive с SHA-256/provenance до destructive processing. Для placeables соблюдай Pixel Snapper → normalize → Aseprite → automatic QA → immutable candidate → exact-SHA visual approval. Для world sprites сохраняй отдельный ref2game-поток. Не смешивай их. PASS generation-preflight разрешает только указанную стадию и не означает scene/runtime/promotion approval.
5. Promotion всегда двухступенчатый. Сначала exact-SHA approved candidate публикуется только в `game-production` (`art/gen` + provenance/QA) отдельным production PR: это tracker-step `promote`. Затем отдельный runtime-publish берёт exact approved bytes и создаёт PR в `main`, заменяя существующий канонический `game/assets/...` файл **на том же пути**: это tracker-step `publish_runtime`. `publish_runtime` не считать `success` только потому, что PR создан — подтвердить merge/resulting runtime SHA. В `main` не должны попадать `art/`, candidates/raw/QA history, production manifests или `outputs/rocket` mirrors. Старые runtime-картинки не сохраняй как `*_old`, `backup`, `v2` и т.п.; rollback выполняется через Git history/revert. Если runtime target/consumer не подтверждён, target отсутствует или production source binary отсутствует, runtime publication `BLOCKED` до устранения конкретного blocker.
6. Пока default branch = `main`, не копируй production-only workflows в `main` ради ручного dispatch. Для Boundary A создай ephemeral command branch `asset-promote/**` от exact current `game-production` SHA и измени только `.asset-command/promote.json`; для Boundary B — `asset-publish-runtime/**` и только `.asset-command/publish-runtime.json`. JSON обязан содержать `asset` и exact `production_base_sha`. Workflow должен отклонить stale base или любой дополнительный diff и убрать command-only commit из рабочей копии до staging. Command branch не является production/runtime history.
7. Каждый объект обязан иметь причинную функцию, инженерную конструкцию и последовательную эволюцию E0–E5. AI рисует физические части; код управляет rig, светом, состояниями, FX. Никаких fake whole-sprite механик, случайных декораций и eventless WORK.
8. Наземный арт согласуй с **утверждённым** видом острова 3/4, масштабом, footprint, anchor, occlusion и land mask. Угол 47° **не подтверждён**: не использовать его как факт. Используй только измеренный generation projection proxy, если он SHA-bound к утверждённому острову, и явно отделяй proxy от неизвестного реального 3D camera angle. Для aircraft действует собственная side/slight-3/4 camera family.
9. До интеграции проверь runtime logical names, era paths, размеры, measured pivots, fallbacks, duplicates, отсутствие конфликтов и scene QA. Не называй design target реализованной механикой. Не объявляй asset готовым без всех применимых QA/approval gates.
10. Не делай прямой push в `main`, не перезаписывай approved production originals, не сливай ветки автоматически. Предлагай отдельную ветку и PR; изменения runtime/CI — отдельно от docs/арт-правил, с migration/rollback plan. Pure asset replacement PR в `main` должен менять только явно разрешённые runtime `game/assets/...` target-файлы. CI и тесты называй пройденными **только** при наличии проверяемого результата.
11. Соблюдай 20-минутный interactive timeout, 5-минутный no-progress watchdog и запрет бесконечного CI polling. Возвращай checkpoint, если не завершено.
12. Каждый ответ о выполненной работе заканчивай проверяемым статусом: `изменено / не изменено`, branch, commit/PR, реально запущенные тесты и их результат, blockers, следующий шаг, ссылки на файлы. При противоречии источников остановись и объясни, что требует решения.

Приоритет — сохранность производственной цепочки и воспроизводимость. Не отступай от правил молча: если выполнение невозможно, покажи точную причину и запроси решение, вместо обхода gate.
