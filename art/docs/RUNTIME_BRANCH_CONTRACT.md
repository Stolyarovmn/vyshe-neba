# Контракт production и runtime

## Назначение и ветки

Этот документ задаёт текущий порядок публикации арта и имеет приоритет над устаревшими описаниями двух обязательных границ и командных веток в других производственных документах. Правила обработки, происхождения оригиналов, проверки SHA и визуальной приёмки сохраняются.

`game-production` хранит брифы, промпты, оригиналы происхождения, обработанный арт `art/gen/`, QA, журналы и производственные инструменты. Оригиналы генераций архивируются на Google Drive; история и свидетельства производства остаются здесь.

`main` хранит игру и только активные runtime-ассеты по каноническим путям `game/assets/...`, которые использует `main:game/src/render/manifest.js`. При публикации арта туда не переносят `art/`, кандидатов, оригиналы и производственные журналы. `clean-src` — историческая ветка, не источник текущего runtime.

## Публикация в main

Публикация — PR в `main`, подготовленный на закреплённых SHA `main` и источника в `game-production`.

1. Сверить роль объекта, состояния и канонический путь с манифестом и кодом на закреплённом SHA `main`. Утверждённый арт не добавляет новую механику сам по себе.
2. Перенести утверждённые байты по объявленным путям `game/assets/...`, заменяя активные файлы на месте. Новые пути требуют явного подключения потребителя в проверяемом PR.
3. В PR перечислить все заменённые пути `game/assets/...`, приложить скриншот из игры и строку **«байты = SHA»** с SHA-256 исходника и каждого соответствующего runtime-файла. Значения должны совпадать; преобразованные файлы проверяются и принимаются как отдельный результат.
4. Запустить применимые проверки игры и сборки на получившемся дереве и указать реальные результаты. Производственная проверка документов не заменяет проверку игры.
5. Приёмка: скриншот из игры принят владельцем. Открытый PR не означает публикацию: она подтверждается слиянием и SHA результата. Прямые изменения `main` и автоматическое слияние запрещены.

Два командных workflow `asset-promote.yml` и `asset-publish-runtime.yml` удалены 2026-11-11. Командные ветки и `.asset-command/*.json` не требуются.

## Один активный файл по каноническому пути

В `main` для каждого заменяемого ассета остаётся один активный файл по каноническому пути. Запрещены `*_old`, `*_previous`, `*_backup`, каталоги резервных версий по датам и дубли только ради отката. Производственные копии и история не зеркалируются в runtime.

## Справочная карта и локальный помощник

[art/runtime/RUNTIME_EXPORTS.json](../runtime/RUNTIME_EXPORTS.json) — справочная карта production-source → runtime-target; не обязательна для публикации. Её исторические записи не доказывают актуальную готовность и не блокируют обычный PR. Реальные пути, потребители, байты и SHA каждый раз проверяются на закреплённых коммитах.

`tools/art_pipeline/publish_runtime_asset.py` остаётся локальным помощником для PR. При его использовании действуют собственные проверки входных данных и точного копирования; сам скрипт не заменяет скриншот, приёмку и проверку результата PR.

## Значение стадий старого трекера

В `art/placeables/PIPELINE_CONFIG.json` пока сохранены технические имена стадий `promote`, `publish_runtime`, `game_tests` для совместимости с журналами. `promote` отмечает утверждённый результат производства; `publish_runtime` — фактическую публикацию в `main`; `game_tests` — проверку игры в runtime-дереве. Эти имена не требуют двух workflow или двух командных веток. Пройденные производственные проверки не означают пройденные проверки игры.

## Откат

Откат — через историю Git: отменить соответствующий PR или восстановить предыдущий Git-объект новым PR. Оригиналы на Drive и свидетельства происхождения не переписываются. Резервные копии внутри `main` не создаются.
