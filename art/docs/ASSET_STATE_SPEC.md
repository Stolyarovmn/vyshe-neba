# Спецификация рабочих состояний объекта

Назначение: описать видимый отклик объекта на события игры. Машина мира `OFF → IDLE → NOTICE → WORK → FINISH → COOLDOWN` изложена в [банке идей](../placeables/IDEA_BANK_PLACEABLES.md); роли и эффекты определяют `main:game/src/data/buildings.js` и `main:game/docs/DESIGN.md` §4.4.

Объём клипов определяется §6. Отдельный механический клип каждому покупаемому объекту не требуется. Решение владельца 2026-11-08: BLOCKED и DENIED показываются только на карточке «База», PRESS = ON-клип, если он существует; создавать отсутствующий клип для нажатия не требуется. Анимация вызывается игровым событием; покачивание целого PNG и бесконечные декоративные циклы запрещены.

## 1. Четыре состояния

| Код | Что это | Когда наступает | Что видит игрок | Рисует арт или код |
| --- | --- | --- | --- | --- |
| `PRESS` | нажатие | тап по купленной и доступной постройке | один показ существующего ON-клипа, отдельный клип нажатия не рисуется | части — арт, интерфейсный отклик и звук — код |
| `ON` | включение, работа | реальное событие старта, аварии, покупки или контракта | движение физических частей для объектов §6; остальным — лампа и дым кодом | части и кадры — арт; свет, вода, дым, звук — код |
| `BLOCKED` | блокировка | условия покупки или работы не выполнены | причина словами из `reasonFull` на карточке «База» | только интерфейс; отдельный вариант спрайта не нужен |
| `DENIED` | отказ | нажатие на заблокированную карточку или недостаток денег/данных | краткий отклик карточки (`kit.denyFx`), причина остаётся видна | интерфейс и звук; состояние постройки не меняется |

`BLOCKED` и ещё не построенный объект соответствуют `OFF`; `PRESS` — отклик на жест; `ON` = `WORK` + `FINISH`; `DENIED` не меняет машину мира.

## 2. Что должна содержать запись

Файл `states.json` рядом с `animation.json` объекта:

Запись содержит ключ игры и эпоху, состояния `PRESS`, `ON`, `BLOCKED`, `DENIED`, причину `why` каждого отклика и режим «меньше движения». Для ON указываются событие `trigger`, физические детали `parts`, действие `motion`, параметры существующего клипа `frames`/`fps`/`loop`, эффекты кода `code_fx`, путь `animation.file` и статус `animation.status`.

Если клип отменён, путь остаётся `null`, статус — «не делать», причина обязательна. Для интерфейсных состояний указываются причины из `reasonFull` и решение о карточке «База». Неприменимое состояние записывается в `not_applicable` с причиной. Описание планируемого действия не доказывает наличие клипа в игре.

## 3. Правила для арта и анимации

1. Анимация складывается из **отдельных физических частей** (стрела, каретка, лампа, дверца), а не из деформации всего спрайта. Опорная часть (основание, плита, стойка) не движется и не вращается.
2. Каждая подвижная часть имеет измеренный pivot после обработки (`animation.json` → `pivot_policy`); пока pivot не измерен, он остаётся `null`.
3. Отклик на `PRESS` начинается за ≤ 0,25 с; длительность существующего ON-клипа при нажатии не сокращается до этого порога. `DENIED` ≤ 0,4 с, `ON` — по событию, не дольше 3 с без новой причины. Частота кадров 8–12, число кадров минимально достаточное: пиксельная анимация читается по ключевым позам.
4. Анимации в GIF/спрайт-листе делаются из частей, утверждённых как неподвижные кадры. Каждый кадр проходит те же проверки проекции, симметрии и размеров, что и статичный спрайт. Кадры строятся на **той же сетке и привязке**, что и опорный кадр; смещение деталей между кадрами — целое число пикселей сетки.
5. Свет, свечение, лучи, дым, пар, тень и звук принадлежат коду и в картинку не запекаются (`style_bible.txt`, «System separation»).
6. BLOCKED и DENIED показываются только на карточке «База»; отдельные стопоры, замки, брезент и заблокированные варианты спрайтов не требуются.
7. `DENIED` не должен выглядеть как поломка: объект остаётся целым, реагирует один раз.
8. Каждое состояние отвечает на вопрос «зачем» (`why`) из игрового процесса и эпохи. Для отменённых клипов новый rig и измерение pivot не требуются.

## 4. Минимальный набор по типам объектов E0

Для всех 14 построек описаны состояния и причины блокировки. Покупки и отказы читаются на карточке «База». Механические клипы требуются только для изометрических объектов и событий из §6; лампа и дым кодом достаточны для остальных. Камера, масштаб и инженерия эпохи заданы в [арт-дирекшене](ART_DIRECTION_HD_PIXEL.md) и [матрице эпох](ERA_DESIGN_MATRIX.md).

## 5. Проверка

Состояние принято, если: (1) для каждой подвижной части есть `pivot` или явная пометка `null` с причиной; (2) кадры совпадают с опорным по размеру холста и привязке; (3) в кадрах нет запечённого света и тени; (4) `why` выводится из эффекта в `main:game/src/data/buildings.js`, паспорта и эпохи; (5) состояние не противоречит `reasonFull` (какие причины блокировки существуют в `game/src/ui/next-steps.js`).

Готово = скриншот из игры принят владельцем. Наличие файла или автоматического отчёта приёмку не заменяет.

## 6. Решение 2026-11-11: где клипы нужны

**Сцена полёта (`base/`): клипы не делаются.** Здания занимают 20–60 px, движение деталей не читается. Существующие кадры `base/anim/` остаются, новые кадры и подвижные слои этой камеры не делать. Старые клипы не подходят изометрическим спрайтам другой камеры.

**База (`iso/`): клипы нужны только для событий, которые игрок видит и ждёт.**

| Постройка | Событие | Объём |
| --- | --- | --- |
| `gantry` | Старт | Стрела/вентиль из отдельных частей |
| `deluge` | Старт | Вода кодом; отдельный растровый клип не нужен |
| `rescue` | После аварии | Ворота и машина |
| `factory` | Покупка | Ворота |
| `logistics` | Контракт | Тельфер |
| Остальные | Реальное событие работы | Лампа и дым кодом; механические клипы не нужны |

Пять прежних ожиданий подвижных слоёв `gantry`, `service`, `observation`, `radar`, `weather` закрыты статусом **«не делать»** для `base/`. Для `gantry` остаётся отдельная задача `iso/` по таблице: она не возобновляет отменённый слой камеры полёта. Это решение задаёт объём будущей работы, а не подтверждает готовность или приёмку изометрических клипов.
